This pass re-tested the fixes from the first review and then attacked the new
cold-stake funding path and the desktop/SPV hardening. It found one **critical

## Fix verification (previous findings)

- **C-1** — `p2cs_cold_spend_authorized` now requires a cold-key signature for
  non-coinstake P2CS spends; the hot-key and P2SH theft probes are rejected, and
  the cold-key positive control is accepted. The extra-push analysis holds: the
  helper reads the last three pushes (after removing a P2SH redeem script), so
  padding cannot shift the signature/pubkey pair.
- **H-1** — the coinstake path now requires `sum(P2CS outputs) >= staked.value`;
  the 1-satoshi burn is rejected.
- **C-2** — `fund_cold_stake` pays the raw P2CS script, which is stakeable and
  covered by R1. The P2SH label is still exposed as an address (see C-3).
- **H-2** — `align_scan_start` moves the scan above the retained floor; the
  regression passes. The alignment skips up to 999 retained blocks (see M-7).
- **H-3** — `notfound` uses `decode_for_peer`; the v3 round-trip probe passes.
- **M-1** — the desktop rebuilds the store on `Lagged`; the rebuild is correct
  but can be triggered by transaction-event lag (see M-5).
- **M-2/M-3** — the data directory is created and the BTC network is selected;
  the UTXO persistence is still network-agnostic (see M-6).
- **L-1** — the WebSocket upgrade uses the `vtr-api-key.<hex>` subprotocol and
  rejects query-string keys; the key is still carried in a header (see L-4).

## Findings

### C-3 — Critical (FIXED in `d11891d`): the cold-stake “address” was a P2PKH
burn address

**Where:** `vtorrent-wallet/src/wallet.rs:106-110`;
`vtorrent-ui/src/pages/StakingPage.tsx:327-330`;
`vtorrent-rpc/src/handlers/wallet.rs:1280-1285`;
`vtorrent-wallet/src/tx_builder.rs:187-190`, `:314-317`.

`generate_cold_stake_keys` computes `script_hash = hash160(redeem_script)` and
returns `Address::from_hash160(&script_hash, PUBKEY_ADDRESS_PREFIX)`. That is a
**P2PKH address whose hash is the P2CS redeem-script hash**, not a P2SH address
and not the raw P2CS script. The UI labels it “P2CS address (fund this)” and
displays it as the funding destination.

A generic send to that address goes through `TxBuilder::recipient` →
`p2pkh_script_pubkey` and creates:

```text
OP_DUP OP_HASH160 <hash160(redeem_script)> OP_EQUALVERIFY OP_CHECKSIG
```

No private key has a public-key hash equal to `hash160(redeem_script)` (that
would require a preimage of the redeem script). The output is unspendable.

**Reproduction:** probe `cold_stake_address_is_a_p2pkh_burn_address` generates
a cold-stake key pair, parses the returned address as P2PKH, and shows the
resulting script is `OP_DUP OP_HASH160 <hash160(script_pubkey)> ...`, not the
P2CS script.

**Impact:** a user who follows the UI instruction and sends VTR to the displayed
address permanently burns the funds. This is the most direct fund-loss path in
the current build.

**Fix applied:** the `address` field was removed from `ColdStakeKeys`, the RPC
response, and the UI. The UI shows the raw `script_pubkey` and `script_hash` and
funds it through `fund_cold_stake`. The probe now reconstructs the old
P2SH-hash-as-P2PKH address to document the bug; the API no longer exposes it.

### H-4 — High (FIXED in `d11891d`): `fund_cold_stake` accepted any P2CS script

**Where:** `vtorrent-rpc/src/handlers/wallet.rs:465-540`;
`vtorrent-rpc/src/handlers/wallet.rs:1203-1225`.

The handler validates only that the hex script classifies as `P2CS`. It does not
bind the script to a key pair generated by this wallet, does not cap the
locktime, and does not show the spending/staking key hashes. A compromised or
malicious frontend can call `fund_cold_stake` with an attacker-controlled P2CS
script (attacker’s spending key, or a far-future locktime) and the user’s
passphrase authorizes the transfer.

**Impact:** funds can be locked to an attacker’s cold key or to an unintended
locktime. The user cannot recover them without the attacker’s key.

**Fix applied:** `create_cold_stake` records the generated script in the
process’s `cold_stake_scripts` set (RPC and Tauri); `fund_cold_stake` rejects a
script not in that set and rejects a locktime above 2,100,000,000. The UI shows
the script hash for confirmation. This binds funding to a script generated in
the same session; a fully compromised frontend that can call both endpoints
remains a residual trust issue.

### H-5 — High (FIXED in `d11891d`): the desktop cold-stake flow called a
missing Tauri command

**Where:** `vtorrent-ui/src/hooks/useNode.tsx:648-654`;
`vtorrent-tauri/src/commands/` (no `create_cold_stake` or `fund_cold_stake`).

`createColdStake` calls `tauriInvoke('create_cold_stake')` when `isTauri()`, but
the Tauri backend has no such command. The `fund_cold_stake` RPC endpoint is
also not exposed through Tauri. The desktop cold-stake panel therefore fails at
“Generate key pair”, and there is no desktop funding flow.

**Impact:** the primary desktop UI cannot use cold staking; the browser/RPC
path is the only one, and it displays the burn address (C-3).

**Fix applied:** Tauri now exposes `create_cold_stake` and `fund_cold_stake`,
and the cold-stake panel has an amount/passphrase/fund flow that uses the raw
script.

### M-5 — Medium (FIXED in `d427181`): desktop lag recovery could be driven
into repeated full rebuilds

**Where:** `vtorrent-tauri/src/commands/node.rs` (the `Lagged` arm).

On any `Lagged`, the desktop collects every block `0..=best_height` while
holding the chain lock and rebuilds the whole store. `Lagged` can be caused by a
burst of `TxUnconfirmed` events, not only by missed block events. A peer that
floods the mempool can force repeated O(chain) rebuilds and block block
processing.

**Impact:** remote denial of service against the desktop node.

**Fix applied:** the `Lagged` arm now checks the store tip/hash against the
chain and skips the rebuild when the store is current. A rebuild still runs
when the store is behind or diverged.

### M-6 — Medium (FIXED in `d427181`): BTC UTXO persistence was
network-agnostic

**Where:** `vtorrent-tauri/src/commands/node.rs` (the `btc_utxos.json` path and
`btc_network` selection).

The BTC wallet now selects the correct network, but the UTXO file is always
`btc_utxos.json` in the wallet directory. Switching from mainnet to
testnet/regtest can load UTXOs and addresses from the other network.

**Impact:** wrong-network balances and failed discovery; a user could mistake
testnet UTXOs for mainnet or vice versa.

**Fix applied:** the Tauri and daemon use `btc_utxos-<network>.json`
(`mainnet`/`testnet`/`regtest`).

### M-7 — Medium (FIXED in `2f580cc`): BTC scan alignment skipped up to 999
retained blocks

**Where:** `vtorrent-btc/src/sync.rs` (`align_scan_start`).

When the checkpoint is below the retained floor, the scan moves to the next
checkpoint boundary + 1. Blocks between the retained floor and that boundary
(up to 999) are never scanned, even though they are inside the retained window.
A birthday or funds in that range are missed.

**Impact:** silent omission of discoverable funds.

**Fix applied:** the scan starts at the requested height. The filter-header
authentication uses the stored filter header for the block before the start,
or the next checkpoint in range. When neither is available it authenticates
from the last checkpoint below the start (a wider range, no skipped scan
blocks); if that anchor is below the retained floor it fails closed instead of
silently skipping.

### L-2 — Low (FIXED in `036afca`): fee estimation assumed 33-byte outputs

**Where:** `vtorrent-wallet/src/tx_builder.rs` (`P2PKH_OUTPUT_SIZE` and
`recipient_script`).

A P2CS output is 60 bytes, but the fee estimate counts 33 bytes per output. The
actual fee is below the target by `27 × fee_rate`; at a high fee rate the
mempool can reject the transaction.

**Fix applied:** `select_coins_with_output_size` charges the actual serialized
output bytes, including the 60-byte P2CS script.

### L-3 — Low (FIXED in `d11891d`): the spending WIF was returned without
cache controls

**Where:** `vtorrent-rpc/src/handlers/wallet.rs` (`ColdStakeResp`).

`create_cold_stake` returns the cold spending WIF in a JSON response with no
`Cache-Control: no-store` and no zeroizing wrapper. The response can be cached
or logged.

**Fix applied:** `create_cold_stake` returns `Cache-Control: no-store`. The
response still contains the WIF string; zeroizing the serialized body remains a
residual hardening item.

### L-4 — Low (FIXED in `aa430e1`): the WebSocket upgrade exposed the API key

**Where:** `vtorrent-rpc/src/ws.rs`; `vtorrent-ui/src/api.ts`.

The key was no longer in the query string, but it was still sent in a header
that proxies and tracing layers may log.

**Fix applied:** `POST /api/v1/ws-token` (API-key protected) issues a
single-use token valid for 60 seconds; the upgrade uses `?token=...` and the
token is consumed. The API key itself is not accepted in the URL or a
WebSocket header. The real WebSocket test covers missing, query-string,
authorized, and token-reuse cases.
